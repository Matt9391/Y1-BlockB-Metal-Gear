    Guided exercise: Write the sprite batcher yourself (see Guided experiences). The engine provides buz::renderer_2d::draw_sprite_instances to draw several sprites in one call. Your batcher will collect sprites and decide which can be drawn together.

    What you will build#

    Each call to buz::renderer_2d::draw_sprite is a separate draw call: a request to the gpu with a small fixed cost. A tile map drawn one tile at a time can therefore produce hundreds or thousands of calls per frame. Preparing those calls takes cpu time, even when each sprite is small.

    In Drawing in 2D, you used instancing to draw a list of sprites in one call. All sprites in that list share a texture, but each can have its own position, size, tint and source rectangle.

    A sprite batcher builds these lists for the game. Instead of drawing each sprite immediately, it queues the sprite. When you flush the batcher, it submits the queued sprites using draw_sprite_instances. Each submitted group is a batch.

    The main constraint is draw order. Later sprites cover earlier sprites, so grouping them must not change which objects appear in front.

    Step 1: measure the current draw calls#

    Press F3 while the game runs to open the stats overlay. Record the draw call count before changing the renderer.

    Counter What it tells you
    Draw callsHow many drawing commands were submitted this frame.
    InstancesHow many instances those commands drew in total.

    After batching, the same scene should need fewer draw calls while drawing the same sprites. A lower draw-call count may improve performance, but it does not guarantee a higher frame rate if something else limits the game.

    Step 3: choose storage and ownership#

    Decide how to store the sprites and their batches:

    • One std::vector of sprites per batch is the simplest, but those vectors must survive between frames if you want to reuse their storage.
    • One std::vector for all sprites, plus batches recording a texture and a (first, count) range, lets you reuse two containers.

    Calling clear() on a vector keeps that vector's capacity. However, clearing a vector of batches destroys its batch objects, and with them the sprite vectors inside and their allocations.

    Also decide how textures stay alive. A texture has to exist when the flush passes it to draw_sprite_instances; after that call you may release it, even in the same frame, because the engine keeps the gpu's copy until the gpu has finished drawing with it. If the batcher stores references or raw pointers, another object must keep the textures alive until the flush. Textures your game keeps for the whole level already live that long. Storing shared pointers in the queue keeps the textures alive without relying on that.

    Your draw() interface can accept a buz::sprite_instance or parameters similar to draw_sprite. Choose the form that makes calls from the game easy to read.

    Check: Fill and flush the queue repeatedly. Once enough capacity has been reserved, drawing within that capacity should not allocate each frame.

    Step 4: use the batcher in the game#

    Queue visible tiles in the order they should be drawn, then queue the characters and other sprites in their required order. Flush at the end of the render pass, while its renderer and camera settings are still active.

    For the initial version, keep everything in one world render pass with one camera. Flush before changing cameras, before the screen pass, and before any direct draw_sprite call (one that skips the batcher) that must appear on top of the queued sprites. Without that flush, the queued sprites are drawn after the direct call and cover it.

    Only queue tiles that intersect the camera's visible area. Skipping objects outside the view is called culling. It avoids storing and submitting sprites that cannot contribute to the image.

    Check: Scroll through the level. A tile at the edge should be drawn as soon as any part of it is inside the window, so no gaps appear, and tiles fully outside the view should not be queued. Check foreground objects and any immediate drawing for ordering mistakes.

    Step 5: compare the result#

    Return to the same scene and camera position used for the first measurement. Open the stats overlay and compare the draw-call counts. Save before and after screenshots showing both the scene and the counters.

    A contiguous layer using one texture now needs one call instead of one per tile. The total depends on how often textures change in the queue; it is not necessarily one call per texture or per layer. Adjacent layers using the same texture may even share a batch.

    Check: Compare the screenshots: the image should look the same as before, with the same sprites in front.

    Going further: layers and text#

    For layers, give sprites an explicit layer number. A stable sort by layer only preserves queue order among sprites with the same layer. You can then batch consecutive runs within the sorted queue.

    Sorting by both layer and texture can reduce draw calls further, but it reorders sprites of different textures within a layer. std::stable_sort only preserves order for entries that compare equal under the comparator; it does not undo this texture reordering. Use it only where reordering is safe, such as non-overlapping sprites. Keep queue order where overlap matters.

    For text, each character is a sprite using a region of the font atlas. Build a text routine that queues those character sprites through the batcher, including their positions, source rectangles and colors.

    Levels#

    Complete the basic level before adding the intermediate and hard features.

    Basic

    • Draw tiles with draw_sprite_instances, grouping each contiguous layer that uses one texture into a single call.
    • Measure draw calls before and after the change.

    Intermediate

    • Build a batcher that groups consecutive sprites by texture and flushes at the end of the render pass.
    • Reuse container capacity so drawing within the reserved capacity does not allocate each frame.
    • Queue only tiles that intersect the camera's view.

    Hard

    • Support layers, preserving queue order where required and grouping by texture only where reordering is safe.
    • Draw text through the batcher too.
