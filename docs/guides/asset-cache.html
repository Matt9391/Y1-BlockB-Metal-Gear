    Guided exercise: Use the 3D template and write the asset cache yourself (see Guided experiences). The functions in asset_management load an asset each time you call them. Your cache will let several objects share an asset that has already been loaded.

    What you will build#

    Suppose ten guards use my_game/models/soldier.glb. If every guard calls buz::load_model, the game repeats the file loading, decoding and mesh uploads for each guard. The guards need separate positions and animation state, but they can share the same model data.

    An asset cache stores loaded assets so the game can reuse them. The first request for the soldier loads its model. Later requests return the model already in the cache.

    You will first cache models by path, then decide who keeps them alive and how to handle failed loads. The examples below are pseudocode.

    Step 1: look up a model by its path#

    Use a map whose key is the asset's path and whose value refers to the loaded model. Check the map before calling the loader:

    The lookup must recognize equivalent paths. For example, my_game/models/soldier.glb and my_game/models/./soldier.glb should use the same entry. Normalize the path before both the lookup and the insertion.

    std::filesystem::path::lexically_normal() can remove redundant path components such as .. Decide on one asset root and one separator format for your keys. Lexical normalization alone does not resolve every way two paths can name the same file, such as symbolic links.

    The input can be a std::string_view, as it is for buz::load_model, but the stored key must own its text. Use a std::string; a stored std::string_view could point at text that no longer exists. If you use generic_u8string() to produce a key, account for its std::u8string return type in C++20 and later rather than assuming it returns std::string.

    Check: Request the same model twice and compare the returned pointers. Then repeat with the two path spellings above. Both requests should refer to the same object.

    Step 2: decide who keeps the model alive#

    The cache and the guards now refer to the same model. You need a clear rule for when that model can be destroyed.

    Start by returning std::shared_ptr<const buz::model>. A shared_ptr keeps an object alive while at least one shared owner remains. The engine also uses shared pointers for textures and meshes.

    There are two choices for the cache itself:

    Stored in the cache What happens when the last guard releases the model? What happens on the next request?
    std::shared_ptrThe cache still keeps it alive.Return the existing model.
    std::weak_ptrThe model is destroyed if no other shared owner remains.Load it again if the weak pointer has expired.

    A cache of shared pointers is a simple starting point for one level. Its clear() releases the cache's references. Models still used by the game remain alive until those users release them too.

    A cache of weak pointers allows unused models to be destroyed sooner. Use lock() to obtain a shared pointer when looking up an entry. If the model has expired, load it again. This can mean repeated loading when characters frequently enter and leave the level.

    Choose one approach and write down why it suits your game.

    Keep shared model data separate from character state#

    Returning a pointer to a const model prevents a guard from directly editing that shared model through the returned pointer. Keep each guard's position and animation playback state outside it.

    For changes such as per-character colors, copy the model and change the copy's per-model settings. Its mesh pointers still refer to the shared meshes, so copying the model does not duplicate the mesh data. Do not modify shared mesh or texture objects expecting the change to affect only one character: the const applies to the model itself, not to the meshes and textures its pointers refer to.

    Check: Release one guard's model pointer while another guard still uses the model. The remaining guard must still be able to draw. Then verify that your cache releases or retains the unused model as intended.

    Step 3: remember failed loads#

    A missing file can be requested repeatedly, perhaps once per update. Without a record of the failure, each request repeats the load attempt and may print the same error again.

    Store a failed result as an entry too. In a shared-pointer cache, an entry containing an empty pointer can mean that loading failed. A key that is absent means the cache has not tried to load it yet.

    For a weak-pointer cache, record failure separately: an expired weak pointer could also mean a valid model was unloaded and should be loaded again. Those cases need different behavior.

    Log the failure on the first attempt. Decide how to retry after the file is fixed, for example by clearing the entry or clearing the cache.

    Check: Request a missing file several times. There should be one load attempt and one error report until you explicitly allow another attempt.

    Step 4: cache other asset types#

    Apply the same lookup and ownership rules to textures and meshes. Separate maps and functions for each type are fine. Once they work, consider whether a template would remove useful duplication without making the code harder to follow.

    The textures of a model need one more step. buz::load_model loads no textures: each node's material only names its image, in material::base_texture, which is a buz::texture_id. Your game loads that image with buz::load_texture(engine, id), and that call loads it again every time, like the other loaders. So loading a model's textures should go through the cache too.

    A texture_id can be the key of the texture map. Two ids are equal when their images have the same bytes, whichever file they came from, and texture_id can be compared and hashed, so it works in a std::map and in a std::unordered_map. When three models carry the same brick image, their three ids are equal and the cache loads the bricks once. For a texture you load by its path, buz::texture_id("my_game/textures/bricks.png") names that image file, so it shares an entry with the same image inside a model. Making that id reads the file to compare its bytes, so make it once, not on every request.

    Think about where the textures are looked up. The cache could fetch them when it loads the model and keep them next to it, or the game could fetch them when it creates an object that draws the model. Either way, drawing a node needs a loaded texture, and the model only holds its id.

    Show counters on screen with draw_text, or log them, and label what each counter measures: cached entries, assets still alive or successful loads, for example. Those numbers are not necessarily the same, especially with weak pointers or cached failures.

    Check: Repeated requests should reuse each asset type. Load two models that use the same image and compare the texture pointers of their nodes. Watch the counters while entering and leaving a level.

    Levels#

    Complete the basic level before adding the intermediate and hard features.

    Basic

    • Loading the same path twice returns the same object; compare the pointers.
    • Normalize paths before using them as cache keys.
    • Return shared models as const; make per-character model changes on a copy.

    Intermediate

    • Report a missing file once rather than on every request.
    • Implement clear() between levels or weak-pointer eviction, and explain the ownership choice.
    • Count loaded assets and show the counts on screen.

    Hard

    • Give the cache exclusive ownership with std::unique_ptr and return small handles to game code.
    • Detect handles to unloaded assets, for example with a generation number.
    • Compare the handle design with shared pointers: explain the benefits and additional work.
