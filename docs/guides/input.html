    Keyboard and mouse state lives in buz::input; grab it from the engine. Every game function receives the engine, so there is no need to store a pointer to it:

    Held, pressed or released?#

    The three keyboard questions differ in when they are true:

    Use is_key_down for continuous actions (moving, shooting a beam) and was_key_pressed for one-shot actions (jump, toggle pause). With is_key_down a single tap would fire on every frame it spans.

    The available keys are the buz::key enum: letters (buz::key::a ...), digits (buz::key::num_0 ...), the arrow keys (left, up, right, down), space, enter, escape, shift, control, tab, backspace and the function keys f1 to f12.

    Mouse#

    The same held/pressed/released trio exists for mouse buttons: buz::input::is_mouse_button_down, buz::input::was_mouse_button_pressed and buz::input::was_mouse_button_released, with buz::mouse_button::left / right / middle.

    Movement#

    Moving a character with the keyboard takes two steps: turn the keys that are held into a direction, then move the character along it. The first step is a key check per direction. The y axis points down, so up is negative:

    Adding that direction to the position every frame moves the character, but two problems show up as soon as you play:

    • Diagonals are faster. Holding w and d gives (1, -1), a vector about 1.41 long, so the character moves 41% faster diagonally. buz::normalize scales a vector to length 1. It has no answer for (0, 0), which has no direction, so only call it when a key is held.
    • The speed depends on the computer. on_update runs once per frame, so a fixed step per frame moves twice as fast at 120 frames per second as at 60. delta_seconds is the time since the previous frame: give the speed in pixels per second and multiply it by that time.

    Mouse look#

    In a first-person game the mouse turns the camera: as long as you move the mouse to the right, you keep turning to the right. The mouse position can't give you that. It stops changing when the cursor reaches the edge of the screen, and in a window the cursor can leave the game altogether, so the next click lands on another program.

    Locking the cursor solves both problems: buz::input::lock_cursor hides the cursor and keeps it inside the window, and buz::input::unlock_cursor shows it again and lets it leave; buz::input::is_cursor_locked tells you whether it is locked. While the cursor is locked, buz::input::get_mouse_position keeps returning the position from before the lock, so a game with a locked cursor reads buz::input::get_mouse_movement instead: how far the mouse moved this frame, in pixels, with positive x to the right and positive y down. The movement is reported whether the cursor is locked or not.

    This code locks the cursor when the player clicks in the window and unlocks it on escape, so the player can always get the cursor back, for a menu or to switch to another program. Locking it once in the constructor would leave the player with no cursor at all until the game closes.

    The movement is not multiplied by delta_seconds, unlike the keyboard movement above. A key that is held says nothing about distance, so the code turns time into distance; the mouse movement already is a distance, the one the player moved the mouse during this frame. A frame that takes twice as long collects twice the movement, and multiplying it by the frame time would make the camera turn faster when the game runs slower.

    The signs follow the engine's 3D world, which has y up and is right-handed: a positive yaw turns to the left and a positive pitch looks up, so moving the mouse to the right or down subtracts. The pitch stays a little below a quarter turn (1.57 radians) in both directions, because past straight up the view turns over and the controls work the other way round. How to build the camera's view matrix from the two angles is up to your game; the matrices and the conventions they follow are in Drawing in 3D.
