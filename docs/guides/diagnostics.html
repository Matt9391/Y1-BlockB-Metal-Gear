    Logging tells you what your game is doing, an assert tells you when one of your assumptions turns out to be wrong, and buz::fatal_error stops a game that cannot go on.

    Logging (core/log.h)#

    There are three severities, and all three format with std::format's {} placeholders. The format string is checked at compile time, so a placeholder without an argument (or the other way around) does not compile. Messages appear in the console window and in buz.log next to the executable:

    Logging is compiled into the Debug and Development builds. In the shipping build (Release) every log call collapses to nothing, so the game pays no formatting cost. Getting started lists the three builds.

    Asserts (core/assert.h)#

    Use BUZ_ASSERT to write down an assumption your code makes. When the condition is false, the assert logs the failed condition with its file and line and stops in the debugger at the call site:

    Asserts are compiled into the Debug build only. In Development and Release they disappear, and the condition is not even evaluated, so never put code with side effects inside one.

    Fatal errors#

    For errors the game cannot recover from, in any configuration, buz::fatal_error logs the message and exits. On Windows it also shows the message in a message box, so the player sees it even when logging is compiled out:

    Exceptions#

    Games rarely use C++ exceptions, and the engine doesn't throw any. A function that can fail returns something you can check instead, such as the checkerboard buz::load_texture returns for a file it cannot load, and buz::fatal_error handles the errors the game cannot go on from.

    The reason is how an exception travels. A throw leaves the current function at once and keeps unwinding the call stack until a catch takes it, and that catch has to deal with it there and then. A game often doesn't want that: a sound that fails to play is better ignored than allowed to abort the rest of the frame.

    Exceptions still have their uses, which is why the engine leaves them switched on in the compiler:

    • While debugging, a throw in code you suspect stops the debugger at that line, with the call stack that led there. Turning exceptions off for the whole project would mean whoever needs them later first has to find the compiler setting that turns them back on.
    • For crash reports, an exception can carry an error from deep inside the game straight to main, instead of passing an error value back through every function in between. Your template's main calls engine.run(game), so a try around that call is where a crash handler can log what went wrong before the game closes.

    The standard library throws too: std::vector::at with an index out of range, std::stoi with text that is not a number. An exception nobody catches ends the game.
