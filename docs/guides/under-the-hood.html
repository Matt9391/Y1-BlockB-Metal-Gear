    You do not need anything on this page to make a game; it describes what happens inside the engine. Everything here is in source/engine: read along.

    Modules#

    The engine is a stack of six libraries (modules), each in its own folder with a public/ folder (headers you may include) and a private/ folder (the implementation). Some also have an internal/ folder: headers only other engine modules include, never a game. A module only uses the modules below it:

    module what it does
    coremath (glm), buz::rect, buz::aabb, color, logging, asserts, timers, random numbers, noise, json, paths
    rhithe "render hardware interface": one small graphics api, implemented with DirectX 12, Vulkan or OpenGL; and what both renderers share: buz::texture, loading images, the compiled shaders
    renderer_2dbuz::world_renderer_2d and buz::screen_renderer: sprites, shapes, text
    renderer_3dbuz::world_renderer_3d: meshes, materials, the built-in shapes, debug views and debug lines, and reading glTF files with cgltf (3D template)
    enginebuz::engine and the main loop; the game classes buz::game, buz::game_2d and buz::game_3d; the window and buz::input, on top of SDL3; buz::audio, on top of miniaudio
    asset_managementloading from the content folder: buz::load_texture, and in 3D buz::load_model and buz::load_mesh

    The 2D template has no renderer_3d, and engine and asset_management come without their 3D files (buz::game_3d and the model loading). Every 3D file sits next to its 2D equivalent: game_3d.h next to game_2d.h.

    Your game links the modules it uses (buz_engine and buz_asset_management, plus buz_renderer_3d in 3D) and includes their headers by module name: #include "renderer_2d/world_renderer_2d.h". CMakeLists.txt in each module folder lists what it depends on.

    Most systems a game uses are split into two classes. Take input. Your game sees buz::input, which answers the questions a game asks: is this key down, where is the mouse? The work behind those answers, recording every keyboard and mouse event SDL reports and starting a new frame, happens in a second class, input_recorder, which only the engine sees. buz::input holds a reference to it.

    The split follows from what a header is for: it holds what its users call, and nothing else. A game never records an event or starts a frame, so those functions are not on the class a game uses. The other systems are split the same way: buz::audio and audio_device, buz::window and native_window, buz::screenshot_saver and screenshot, buz::world_renderer_2d and sprite_pass. For input, audio, the window and screenshots the engine owns both halves and hands your game its half through buz::engine::get_input, get_audio, get_window and get_screenshots.

    The renderers belong to your game instead. buz::game creates the screen renderer, and buz::game_2d or buz::game_3d the world renderer; each is handed to the draw function that uses it. The engine keeps one screen renderer of its own, for the stats overlay.

    Loading works differently again: buz::load_texture, buz::load_mesh and buz::load_model are free functions in asset_management that take the engine.

    The frame#

    buz::engine::run brings the modules up in dependency order and runs the main loop until the window closes:

    1. hand SDL's events to the systems they belong to: keyboard and mouse to buz::input, closing the window to the end of the loop;
    2. update your game (buz::game::update calls your on_update);
    3. start a frame on the gpu (wait until the gpu is done with this frame's buffers, clear the screen and the depth buffer);
    4. draw your game: on_render_world, then on_render_screen;
    5. show the frame.

    The cpu does not wait for the gpu to finish a frame before starting the next: there are two frames in flight. While the gpu draws frame 10, the cpu already prepares frame 11. Everything the cpu writes per frame (vertex data, instance lists) therefore exists twice, one copy per frame in flight, and a fence tells the cpu when the gpu has finished with a copy so it can be reused.

    Three graphics apis, one renderer#

    DirectX 12 runs on Windows only; Vulkan and OpenGL run on Windows and Linux. Instead of three renderers, the engine has one, written against its own small graphics api in rhi/internal/rhi/: buffers, textures, pipelines and a command list with the handful of commands the renderers need.

    A build compiles one implementation (a backend) of that api. Your template builds OpenGL, and also has DirectX 12 (Windows) or Vulkan (Linux) for when you want to try a modern api (Getting started shows how to switch). A game never switches graphics api while it runs, so the choice is made when building, and the rhi needs no virtual functions.

    Each rhi class keeps the backend's data in a native object, the pimpl idiom. Every backend has one file per class (backend/gpu_texture.cpp, backend/device.cpp, ...) that defines both the class and its native, and CMake compiles only the chosen backend's folder: no source file asks which backend it is.

    Your template holds the backend of its OS: rhi/private/d3d12 in the Windows zip, rhi/private/vulkan in the Linux zip. The two have the same files and the same structure:

    file job
    adapter_selectionfinds every graphics card and scores it (video memory first), see below
    devicecreates the api's device on the chosen card
    command_queuesubmits recorded commands, and tracks with a fence (Vulkan: a timeline semaphore) what the gpu has finished
    swap_chainthe images that end up on screen
    descriptor_heapslots for textures, so shaders can find them
    pso_cachesaves compiled pipelines to disk, see below
    backend/the native half of every rhi class, one file per class, built on the files above

    Keeping the two alike is deliberate: read the same file in both and you see how the two apis solve the same problem.

    OpenGL#

    The OpenGL backend (rhi/private/opengl) is much smaller, because OpenGL does a lot of that work for you. The driver owns the window's buffers, so there is no swap chain; it waits when the cpu gets too far ahead, so there is no fence; and it keeps a texture alive until the gpu is done with it. What is left is the drawing itself:

    file job
    gl_functionsthe list of every OpenGL function the backend calls, loaded from the driver by name at start-up
    gl_callBUZ_GL_CALL(...): in Debug builds, asks OpenGL after every call whether it failed, and logs the call that did
    backend/the native half of every rhi class, one file per class

    The OpenGL backend uses OpenGL 3.3 core, the version most OpenGL tutorials teach (such as LearnOpenGL), and only what OpenGL ES 3.0 has too, the OpenGL of phones and of web browsers (WebGL 2).

    OpenGL has no pipeline object: where DirectX 12 and Vulkan compile all the state of a draw into one object up front, set_pipeline sets each piece of state with its own call (glEnable(GL_BLEND), glDepthFunc, ...). That is easy to read, and it is also why OpenGL is harder to make fast: the driver only learns at the draw what the draw needs.

    The same picture#

    The backends must draw the same picture, and the way to check that is to compare screenshots. -screenshot=file.png saves one frame with a fixed time step and with the keyboard and mouse ignored, so every run draws exactly the same frame, and the screenshots of two backends can be compared pixel by pixel.

    The screenshots match, with one exception. OpenGL counts pixel rows from the bottom of the window, DirectX 12 and Vulkan from the top. The engine corrects for that, but a pixel that lies exactly on the edge between two texels can still round the other way.

    Graphics card selection#

    A laptop often has two graphics cards: a weak one built into the processor and a faster one of its own. Like Unreal, the engine looks at every card in the machine before it picks one. Each card gets a score, mostly from its dedicated video memory and partly from what it supports, and the highest score wins. Software renderers score zero, so they are only used when there is no real card. The console shows the score of every card at startup.

    You can override the choice with engine_settings::gpu_preference. buz::adapter_preference::lowest_score picks the weakest card, which is a quick way to see how your game runs on low-end hardware. buz::adapter_preference::software draws without a graphics card at all: slow, but it runs anywhere.

    OpenGL has no way to choose a card. It always draws on the one the driver picks.

    Lifetimes#

    When the cpu is done with a buffer or texture, the gpu may still be using it, for a frame or two, because of the frames in flight. Destroying it right away would pull it out from under the gpu. So a released resource waits in a queue until the fence says the gpu has passed the last frame that used it, and only then is it destroyed. OpenGL does that waiting itself, so its backend frees a resource right away.

    At shutdown, every resource must be gone before the device is. A resource that is still alive then stops the engine with an error, in every backend.

    Shaders#

    The shaders are written once, in HLSL, in /shaders. The shader_compiler tool (in source/tools, using Microsoft's DXC compiler) compiles every file for the build's graphics api: to DXIL (.cso) for DirectX 12, to SPIR-V (.spv) for Vulkan, or to GLSL (.glsl) for OpenGL. For OpenGL, DXC first makes SPIR-V, and SPIRV-Cross turns that into GLSL, so you write HLSL for every backend. Open a .glsl file in the build folder to see what your shader became.

    The file name picks the stage: foo_vs.hlsl is a vertex shader, foo_ps.hlsl a pixel shader. To add a shader, drop the file in /shaders and build; like C++ files, a shader is only recompiled when it changed.

    Per-draw data (a sprite's transform, color and texture area) goes to the shader as a small block of constants: root constants in DirectX 12, push constants in Vulkan, a uniform block in OpenGL. Vulkan only promises 128 bytes of those, so that is the budget for everything a single draw needs.

    Pipeline caching#

    A pipeline holds everything about how a draw is done, including its shaders. Creating one makes the driver compile the shader bytecode into instructions for your particular gpu, and that is slow enough to notice at startup. So the engine saves the pipelines it created to cache/pso_cache_d3d12.bin or cache/pso_cache_vulkan.bin when the game closes, and loads them on the next start. When the cache no longer matches, after a driver update, on another card or after a shader changed, it is thrown away and rebuilt.

    You can see the cache at work in the console. With DirectX 12, a pipeline is created from scratch on the first run and loaded from the pso cache after that. Vulkan hands the cache to the driver, which uses what it can, so the engine logs created either way and the difference only shows in how fast the game starts. OpenGL has no pipeline objects to save, so the engine has no cache for it; most drivers keep a shader cache of their own.

    Textures#

    The engine's texture loader (rhi/internal) uses stb_image, so png, jpg, bmp and tga all work. The gpu cannot read cpu memory directly: pixels are written into an upload buffer, the gpu copies them into the texture, and a descriptor lets shaders find it. All of that is behind buz::load_texture and buz::create_texture.

    Textures are sampled through one sampler chosen at startup, so its filter cannot change mid-run: engine_settings::sampler_filter.

    Sprites and text#

    Every buz::renderer_2d::draw_sprite call is one draw call of the same unit square, with its own transform, texture area and tint as constants. buz::renderer_2d::draw_sprite_instances writes a list of sprites into the frame's vertex memory instead and draws them all in one call (see Sprite batching).

    Text is sprite sheet drawing: one atlas texture holds every character in a fixed grid (content/fonts/font_8x8.png, based on the public domain font8x8 by Daniel Hepper), and every character is one sprite.

    3D#

    renderer_2d and renderer_3d both sit on the rhi, and neither includes the other. Yet a game can draw sprites and meshes in the same on_render_world, into the same frame.

    That works because both record into the same command list. While your game draws, the engine's render context holds the frame's command list. Every renderer keeps that context, creates its pipelines when it is constructed, and starts its own work on its first draw of a frame. buz::world_renderer_3d sets its own pipeline before it draws a mesh. Before its next sprite, the 2D side checks which pipeline is set (rhi::command_list::get_pipeline) and sets its own again if it has changed. Neither renderer needs to know the other exists.

    The mesh shaders are shaders/mesh_vs.hlsl and mesh_ps.hlsl: read them.
