    A game written for an earlier version of the engine doesn't always build with a newer one, because the engine's headers and classes change between versions. Most of those changes show up as compile errors at the line to fix. The exception is the change to textures in 5.0: after the update, models still load and draw without any error, but without their textures.

    You can tell which version a game was written for from the class it derives from:

    your game written for
    derives from buz::game, and a 3D game has a world_renderer_3d member of its own3.0
    derives from buz::game_2d or buz::game_3d, from engine/game_2d.h or engine/game_3d.h4.1
    derives from buz::game_2d or buz::game_3d, from game_framework/game_2d.h or game_framework/game_3d.h5.0, 5.1, 5.1.1 or 5.1.2

    The newest changes come first. A game written for an older version needs every section from its version on, starting at the bottom: a game written for 3.0 needs all of them, starting with From 3.0 to 4.1.

    From 5.1.1 to 5.1.2#

    Nothing in your game has to change. 5.1.2 only rewords parts of the documentation; the engine's code is the same as in 5.1.1.

    From 5.1 to 5.1.1#

    Nothing in your game has to change. 5.1.1 adds buz::model_import_options: buz::load_model, buz::load_mesh and buz::import_model can repair a model whose normals point inward or whose texture coordinates lie outside 0..1, which happens with files saved out of a web viewer. Models explains when you need it.

    If you used the patch for this that was sent around for 5.1, the option is now called buz::orient_normals instead of buz::repair_normals.

    From 5.0 to 5.1#

    Include core/filesystem.h where you use buz::fs#

    In 5.0, engine/audio.h included core/filesystem.h without using it, so a file that included engine/audio.h could also use buz::fs and std::filesystem without including anything for them. In 5.1 an engine header only includes core/filesystem.h when its own declarations use it, so a file of yours that relied on getting it from engine/audio.h stops compiling. Visual Studio then says "'fs': the symbol to the left of a '::' must be a type" and "'list_content_files': is not a member of 'buz'", or "'filesystem': is not a member of 'std'".

    Include it yourself, at the top of the file that uses it:

    That header gives you buz::fs::list_content_files and buz::fs::path, which is std::filesystem::path. The engine's own functions, such as buz::load_texture and buz::audio::play_sound, take paths as text and don't need it.

    From 4.1 to 5.0#

    Models are drawn without textures until you load them#

    The compiler doesn't report this change. In 4.1 buz::load_model loaded every image the model file uses and stored it in each node's material, and world.draw(*node.shape, node.look, transform) drew the node with it. Every call to load_model loaded those images again, so ten guards that each loaded the soldier had ten copies of his textures on the graphics card.

    In 5.0 load_model loads no textures. A node's look.base_texture is now a buz::texture_id: it names the image (a file next to the model, or an image inside a .glb) without loading it, and two ids that name the same image are equal, so your game can decide to load each image once. The three-argument draw draws the mesh in the material's plain color. A game that only updated the engine therefore still builds and runs, and draws every model in flat colors.

    To get the textures back, load each node's image with buz::load_texture(engine, id), which is declared in asset_management/model_loading.h, and pass the texture to the four-argument draw. Before, in on_render_world:

    The game classes moved to game_framework#

    buz::game, buz::game_2d and buz::game_3d moved out of the engine module into a module of their own, game_framework. The engine itself now runs a buz::playable, an interface that buz::game implements; main and engine.run(game) stay the same, and your game still derives from game_2d or game_3d. Change the include:

    A 2D game makes the same changes with game_2d.h and without buz_renderer_3d.

    Textures moved to render_core#

    buz::texture moved from rhi/texture.h to render_core/texture.h. The rhi module, the layer that talks to the graphics api, is now for the engine only: a game can't include its headers, and configuring fails when a game links it. rhi/settings.h is gone with it. buz::adapter_preference and buz::vsync are now declared in engine/engine_settings.h, and buz::texture_filter in render_core/texture_filter.h, which engine_settings.h includes, so a game that sets them in its engine settings needs no include of its own.

    One content folder, with a folder per game#

    In 4.1 the files the samples used were at the top of the content folder (fonts/, textures/, models/), and a game could also have a content folder of its own in source/games/<game>. In 5.0 there is one content folder, content at the top of your template, with a folder per game in it: the files of sample_3d are in content/sample_3d, and the files that every game may use are in content/shared. A game that still has a source/games/<game>/content folder stops the configure step with a message that says where to move it.

    That changes these paths:

    4.1 5.0
    "fonts/font_8x8.png""shared/fonts/font_8x8.png"
    "textures/checker.png""shared/textures/checker.png"
    "models/crate.gltf", "models/soldier.glb" and the other sample files"sample_3d/models/crate.gltf", and so on; the 2D sample's in "sample_2d/..."

    Both samples load the font, so most games need the first change. Move your own files into content/<game>, where <game> is your game's folder name, and put that folder name at the front of each path: "textures/player.png" becomes "my_game/textures/player.png". If they were in source/games/<game>/content, move what is inside that folder to the top content folder.

    A wrong path doesn't stop the build. buz::load_texture logs the error and returns a magenta placeholder, and buz::load_model logs it and returns an empty std::optional, so check the console after the first run.

    Smaller changes#

    • joint_pose is now buz::node_transform, and model_node::local_pose is now local_transform; keyframe_clip::frames and get_rest_pose use the new type. The type is the same, only its name changed: it describes the place of any node, not only of a joint. Find and replace both names.
    • The built-in mesh shaders shaders/mesh_vs.hlsl and mesh_ps.hlsl are now diffuse_vs.hlsl and diffuse_ps.hlsl. This only matters if you changed them: your changes are in files the engine no longer reads. In 5.0 you don't need to change the engine's shaders, because a game can draw its meshes with shaders of its own (see Drawing in 3D).
    • A renderer draws only while the render function that received it runs. A game that kept a pointer to a renderer and drew with it from on_update stops at an assert.

    New in 5.0#

    These don't require changes to your game:

    • buz::input::lock_cursor and buz::input::get_mouse_movement, for mouse look in a first-person or third-person game (Input).
    • buz::import_model reads a model onto the cpu without uploading anything, and buz::make_primitive builds the triangles of the built-in shapes (Models, Drawing in 3D).
    • buz::set_surface_shading draws a world's meshes with your own shaders, and buz::world_renderer_3d::set_shader_data hands them data (Drawing in 3D). Besides that data, the shaders receive each mesh's world matrix and the camera's position, so they can light or fog a surface by where it is in the world.
    • buz::fs::list_content_files lists the files in a folder of the content folder, and buz::engine::get_settings returns the settings the engine runs with, including those from the command line.

    From 3.0 to 4.1#

    The game class owns its renderers#

    In 3.0 every game derived from buz::game, and on_render_world received a buz::world_renderer_2d, also in a 3D game, which didn't use it. A 3D game made its own buz::world_renderer_3d as a member and drew with that.

    In 4.1 the base class owns the world renderer and hands the right one to on_render_world. A 2D game derives from buz::game_2d and gets a buz::world_renderer_2d; a 3D game derives from buz::game_3d and gets a buz::world_renderer_3d. The base class creates its renderers on the graphics card in its constructor, so it needs the engine, and your constructor has to pass it on. For a 3D game, before:

    After:

    The m_world_3d member is gone, so every function of yours that drew with it now takes the renderer as a parameter: a draw_level() becomes draw_level(buz::world_renderer_3d& world), called from on_render_world with its world.

    A 2D game changes the same way: derive from buz::game_2d (include engine/game_2d.h) and put buz::game_2d(engine) first in the constructor's initializer list, before your own members.

    Loading moved to asset_management#

    The functions that load files, and create_mesh, moved to a new module, asset_management. The types they return stay where they were, so renderer_3d/model.h and renderer_3d/mesh.h still declare buz::model and buz::mesh. Change the includes:

    3.0 4.1
    engine/texture_loading.hasset_management/texture_loading.h
    renderer_3d/model.h, for buz::load_model and buz::load_meshasset_management/model_loading.h
    renderer_3d/mesh.h, for buz::create_meshasset_management/model_loading.h

    A game can only include the headers of the modules it links, so add buz_asset_management to LINKS in your game's CMakeLists.txt:

    See-through pixels#

    This needs no change to your game: 4.1 added alpha_cutoff to buz::material. Pixels whose alpha is below it are not drawn at all, which is how a flat quad becomes a railing or a fence. Drawing in 3D explains it.
