    Needs the 3D template. A 3D game derives from buz::game_3d and must link buz_renderer_3d.

    A 3D game draws its world with a buz::world_renderer_3d. buz::game_3d owns it and hands it to on_render_world every frame, the same way a 2D game gets its buz::world_renderer_2d. The hud is drawn as in a 2D game, with the screen renderer in on_render_screen (see Drawing in 2D).

    The renderer only exists in on_render_world, so everything that uses it happens there: drawing, the camera and the debug views below.

    Built-in shapes#

    Five shapes, each drawn at a position (its center) and a size:

    function shape
    buz::world_renderer_3d::draw_boxa cube
    buz::world_renderer_3d::draw_spherea sphere
    buz::world_renderer_3d::draw_planea flat square facing up
    buz::world_renderer_3d::draw_cylinderan upright cylinder
    buz::world_renderer_3d::draw_octahedrontwo pyramids base to base

    Unlike sprites, the order you draw shapes in doesn't matter: nearer surfaces hide farther ones, because the engine keeps a depth buffer.

    With a few boxes and cylinders you can block out a whole level ("greybox" it) before any art exists. sample_3d does exactly that.

    Materials#

    A buz::material says how a surface looks: a color, optionally a texture (multiplied with the color), and whether it is lit.

    Lit surfaces get one fixed light from above plus a little ambient light, so shapes read clearly without any setup.

    Some surfaces have holes in them. On the first PlayStation, where every triangle counted, a railing or a fence was usually one flat quad whose texture has alpha 0 between the bars. Modern games often model the bars instead, but the same trick is still common for leaves, grass and wire fences. Set alpha_cutoff to cut the transparent parts out: pixels whose alpha (texture times color) is below it are not drawn at all, so you see what is behind them, whatever order you draw in.

    Without a cutoff, alpha between 0 and 1 blends with what is already on screen, which makes water or glass see-through. Blending can only mix with what has been drawn before: an object behind the glass that is drawn after it does not show through. So draw blended surfaces after everything else.

    Your camera#

    Until you set a camera, buz::world_renderer_3d shows the world from a fixed spot up and to the side of the origin, looking at it. Your own camera is two matrices, handed to buz::world_renderer_3d::set_camera:

    • the view matrix moves and turns the world so the camera sits at the origin, looking down -z, with y up;
    • the projection matrix maps what the camera sees onto the window.

    The conventions your matrices have to follow:

    • The world is right-handed with y up: x to the right, y up and z towards the viewer. One unit is a meter.
    • Matrices are glm's: stored by column (m[column][row]), and a position is a column vector transformed as v' = M * v. The translation lives in the last column, m[3].
    • After the projection and the divide by w, x and y run from -1 to 1 across the window, and depth runs from 0 at the near plane to 1 at the far plane on every graphics api buz uses. A projection made for OpenGL's -1 to 1 depth (glm's plain perspective) clips the wrong things.

    Debug views#

    When a model looks wrong, it helps to see it without its textures and light. Press F1 while the game runs to draw only the edges of every triangle. Press F2 to draw every surface at its plain color, without lighting, so you can tell a dark texture from a surface that faces away from the light. Press F4 to hide the debug lines described below, and again to show them.

    The engine handles these keys in every 3D game, so your game doesn't check them. To use other keys, see debug_controls in Getting started.

    Debug drawing#

    Lines that show what your code thinks is there: colliders, a guard's view, a patrol path, a ray you cast. When the game misbehaves, draw what it believes and the mistake is usually obvious.

    Debug lines are depth tested like every other surface, so a wall in front of a line hides it. They start switched on, and F4 hides all of them at once (see Debug views), so the calls can stay in your code instead of being removed when you are done debugging.
