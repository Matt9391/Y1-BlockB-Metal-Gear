    Guided exercise: Write the animation helper yourself (see Guided experiences). The engine can draw part of a sprite sheet with buz::renderer_2d::draw_sprite and a source buz::rect. Your helper will choose which part to draw as the animation plays.

    What you will build#

    A sprite animation displays a sequence of images over time. A sprite sheet stores those images in one texture, and each image in the sequence is a frame. To animate the sprite, change the source rectangle passed to draw_sprite.

    The example in Drawing in 2D does this directly in on_render_world:

    This works for one looping animation. A character with idle, run, jump and death animations needs more information: where each sequence starts, how many frames it contains, how fast it plays and whether it repeats. The game also needs to know when an animation has finished.

    Put that information and the playback logic into two types:

    Type What it stores When it changes
    sprite_animationFirst frame, frame count, playback speed and looping setting.When you define or edit the animation.
    sprite_animatorThe selected animation and elapsed playback time.While a character plays an animation.

    Each character needs its own animator so its playback can progress independently. The animation definitions can be shared.

    The remaining examples are pseudocode. They assume equally sized cells without gaps, numbered left to right and then row by row. Each animation uses a consecutive range of those cells.

    Step 1: select a frame without playing the animation#

    First, write a function that converts a frame index into a source rectangle. Store the cell size as frame_size (a buz::vec2) and the number of columns in the sheet as columns.

    For example, frame 5 in a sheet with four columns is in column 1, row 1, counting from zero. With 64 by 64 cells, its source rectangle runs from (64, 64) to (128, 128).

    buz::rect stores its minimum and maximum corners, not a position and a size. Use texture pixels for these coordinates, regardless of how large the sprite will be drawn in the game.

    Check: Draw a few frames by specifying their indices directly. Include the last frame of one row and the first frame of the next row.

    Step 3: calculate the current frame from elapsed time#

    The animator records elapsed time in seconds. Update that time once per game update, then calculate which frame should be shown:

    elapsed * fps converts playback time into a frame number within the animation. At 8 frames per second, 0.25 seconds selects local frame 2. Adding first_frame converts that local number into the sheet's cell index.

    For a loop, modulo wraps back to the first frame. For an animation that plays once, min keeps the index on the last frame after the end. These calculations assume non-negative elapsed time.

    The animation frame rate is separate from the game's update or rendering rate. Deriving the frame from elapsed time lets playback keep the same speed even if the game performs a different number of updates per second. At a low update rate, some animation frames may be skipped.

    Check: Play a loop and a one-shot at different update rates. The loop should repeat at the same speed; the one-shot should hold its final frame.

    Step 4: switch animations without restarting every update#

    Add play() to select an animation and reset its elapsed time. If that animation is already selected, leave it playing:

    Use a stable animation identity for that comparison, such as an ID or a reference to a definition that stays alive. If the animator stores a reference, the definition must outlive its use by the animator.

    The early return matters because the game may request play(run) every update while a movement key is held. Resetting time on every request would keep restarting the animation instead of letting it progress.

    This example gives death priority over jumping, and jumping priority over movement. Add other states according to your game's rules. If you need to deliberately replay the same animation, provide a separate restart operation or an explicit restart option.

    Check: Hold a movement key. The run animation should continue rather than repeatedly show its first frame. Releasing the key should start idle.

    Step 5: report when an animation has finished#

    A one-shot must give its last frame time to be displayed before reporting completion. With frame_count frames shown for 1 / fps seconds each, its duration is frame_count / fps seconds.

    For example, four frames at 8 frames per second last 0.5 seconds. The last frame starts at 0.375 seconds; the animation finishes at 0.5 seconds. Afterwards, the animator continues returning that last frame until the game selects another animation.

    The game decides what completion means. A shot might return to idle; a death animation might stay on its last frame while the game shows a game-over screen. Check which animation finished before choosing a response.

    Check: Confirm that a one-shot reports completion only after the last frame's display interval. A loop should never report completion.

    Connect animation to gameplay#

    An animation finishing and a gameplay action finishing are not always the same event. A jump animation may reach its last frame before the character lands. Use the character's gameplay state to decide when to leave that animation.

    Animation Repeats? Example start condition Example end behavior
    IdleYesCharacter is standing still.Switch when the character acts.
    RunYesCharacter is moving on the ground.Switch when movement or state changes.
    JumpNoCharacter jumps.Hold the last frame if needed; switch on landing.
    ShootNoCharacter fires.Return to the appropriate state when the animation finishes.
    DieNoHealth reaches zero.Hold the last frame; let gameplay handle completion.

    Levels#

    Complete the basic level before adding the intermediate and hard features.

    Basic

    • Test frame_rect(index, ...) separately before adding playback.
    • Keep sprite_animation as fixed definition data, without elapsed time.
    • Store elapsed time in the animator and derive the current frame from it.
    • Play looping animations at their defined speeds.

    Intermediate

    • Wrap looping animations and hold the final frame of one-shots.
    • Keep playing when play() requests the current animation again.
    • Use finished() so gameplay can respond to one-shot completion.
    • Keep timing calculations out of on_render_world; use current_frame_rect().

    Hard

    • Load animation definitions from data, such as a json file per character.
    • Animate layers independently, such as walking legs and a shooting torso.

    See Drawing in 2D for buz::renderer_2d::draw_sprite and Utilities for buz::rect and the timing helpers.
