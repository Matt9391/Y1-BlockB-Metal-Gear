    What you get#

    Your template is a zip: the engine, one or more starting games and the scripts to build them. There are two templates:

    template starting games
    2Dsample_2d
    3Dsample_2d, sample_3d

    The 3D template is the 2D template plus the 3D modules, so almost every guide applies to both: a 3D game still draws its hud with sprites and text, reads input, plays sound and loads json. Only Drawing in 3D, Models and the 3D exercises need the 3D template.

    Each template comes in a Windows and a Linux zip. They hold the same code; only the scripts differ.

    Building your template#

    Windows#

    You need Visual Studio 2026 with the Desktop development with C++ workload. That workload also installs the Windows SDK and CMake, so there is nothing else to install: generate.bat finds the CMake that comes with Visual Studio on its own.

    Press F5 in Visual Studio. A window opens with the "catch the ball" game, and a console window next to it shows the engine's log.

    Linux#

    You need a C++20 compiler (GCC 13 or Clang 17 or newer), CMake 3.25 or newer, Ninja, a graphics driver with OpenGL 3.3 (Vulkan 1.3 if you switch to Vulkan, see below), and the development headers SDL needs to open a window. The template's README lists the exact apt command for Ubuntu and Debian.

    run.sh opens a window with the "catch the ball" game and prints the engine's log in the terminal.

    The template has no solution file and no build/ folder. CMake writes absolute paths into both, which only work on the machine that created them, so the generate script makes them for you. You can delete build/ at any time. When a build starts behaving strangely, deleting it and generating again is often the quickest fix.

    Generating a solution is optional. Visual Studio, VS Code and CLion can also open the template folder directly: they read CMakePresets.json and give you IntelliSense, breakpoints and debugging without a generated project.

    The scripts#

    Windows Linux what it does
    generate.bat [-open] [preset]./generate.sh [preset](re)creates the build/ folder; -open opens the solution afterwards; the preset picks the graphics api, see below
    build.bat [-debug|-release]./build.sh [-release]builds everything; debug is the default
    run.bat [-release] [-game=name] [-setting=value...]./run.sh [-release] [-game=name] [-setting=value...]runs a built game, sample_2d unless you pick another; other -setting=value arguments go to the game
    package.bat [-game=name] [-web] [-development]./package.sh [-game=name] [-web] [-development]packages a game to share (shipping or development build), see Sharing your game below

    Your first game#

    Below is a complete game: a class that draws a ball in the middle of the window, and the main() function that starts it.

    The class derives from buz::game_2d, which is how the engine knows what to run and that the game's world is 2D; a 3D game derives from buz::game_3d instead (Drawing in 3D). Its constructor receives the engine and passes it on to game_2d, which uses it to create the renderers the game draws with. Then it loads what the game needs: here one texture, kept in a member so that it stays loaded for as long as the game exists. When the game is destroyed, the member goes with it and the texture is released.

    While the game runs, the engine calls three of the game's functions every frame, in this order: on_update, on_render_world and on_render_screen. on_update is where the game reacts to input and moves things. The other two draw: first the world, then the hud on top of it. Each gets the renderer it draws with: on_render_world the game's world renderer, and on_render_screen its screen renderer (Drawing in 2D explains the difference). You only override the ones you need, which is why this game has just on_render_world. The three functions are protected, because only the engine calls them, through the base class.

    main() creates the engine first and the game second, because the game needs the engine to load its textures. C++ destroys local variables in reverse order, so the game and every texture it holds are gone before the engine shuts the graphics card down.

    To run this code yourself, set up a game of your own as described in Adding another game below, put the code in it, and copy the ball from content/sample_2d/textures to content/my_game/textures. The ball appears in the middle of a 1280 by 720 window, and the engine's log appears in the console next to it.

    In a real game, the game class doesn't do all the work itself. The player, the enemies and the level are usually classes of their own, in separate files, and the game class creates them and updates them every frame. Adding files to your game below shows how to add them.

    Where your files go#

    The images, sounds and other files your game loads live in the content folder of your template. Every game has a folder of its own there, named after the game: the files of sample_2d are in content/sample_2d, those of sample_3d in content/sample_3d. Two games can then each have a textures/ball.png without one replacing the other. Files that every game may use are in content/shared: the engine's font (shared/fonts/font_8x8.png) and a checker texture (shared/textures/checker.png).

    Every engine function that loads a file takes the file's path as text, relative to the content folder, with / between folders, so the path starts with your game's folder:

    Sometimes the game doesn't know the names in advance, for example when it loads every level that is in my_game/levels. buz::fs::list_content_files (core/filesystem.h) lists every file in a folder of the content folder and in its subfolders. It returns them as paths in the same form, so each one can go straight to a loading function, and sorted, so they load in the same order on every run:

    A relative path needs a folder to start from. Normally that is the folder the program was started from (a.k.a. the working directory), but that folder changes with how you start the game: Visual Studio starts it in one folder and a terminal in whatever folder the terminal is in. The engine therefore doesn't use the working directory. Every build copies your content folder next to the executable, and the engine always looks for content there.

    The engine also writes files: screenshots, and the json files you save with buz::save_json. A relative path for those starts from a folder that belongs to your game alone, saved/<game> next to the executable (for example build/Debug/saved/sample_2d). Every game in your template builds into the same folder, so if they all saved their files next to the executable, one game's save file could overwrite another game's.

    Adding another game#

    Every folder in source/games with a CMakeLists.txt is a game. To start a new one, say awesome_game:

    1. Copy the sample_2d folder to source/games/awesome_game.
    2. In the copied CMakeLists.txt, replace sample_2d with awesome_game everywhere. The run and package scripts use that name to find your game: you pass it as -game=awesome_game.
    3. Rename the class and the files in private/ as you like.
    4. Create content/awesome_game for the game's own files. The copied code still loads its ball and sound from content/sample_2d; change those paths to awesome_game/... once the files are in the new folder.
    5. Run the generate script again and build. Visual Studio now lists awesome_game next to the other games. To run and debug the new game from Visual Studio, right-click it and choose Set as Startup Project. To run it without Visual Studio, use run.bat -game=awesome_game. You can also package it right away, without any extra setup: see Sharing your game.

    The CMakeLists.txt you copied is a single call:

    BUZ_GAME turns the folder into a game: an executable built from every source file in its private folder, with the shaders compiled and the content folder copied next to it. LINKS names the engine modules the game uses. The engine is split into modules, each a library with its own headers, and linking one adds its code to your game and lets your game include its headers. buz_engine is the engine itself: the window, the main loop, input and audio. buz_game_framework holds buz::game_2d and buz::game_3d, the classes your game derives from, which is why their headers start with game_framework/. buz_asset_management loads textures, and in the 3D template also models. A 3D game links buz_renderer_3d as well, as the CMakeLists.txt of sample_3d shows. Under the hood explains what each module does and what it is built on.

    Adding files to your game#

    Game sources are discovered automatically: every .cpp/.h file under your game's private folder is part of the game. To add a class:

    1. Create the file(s) in source/games/<your_game>/private, from the file explorer, or in Visual Studio via right-click on the project → Add → New Item....
    2. Build. CMake notices the new file and updates the project; Visual Studio asks to reload, click Reload All, then build again.

    Be careful with Visual Studio's Add → New Item... dialog: it suggests the project folder inside build/ as the place for the new file, for example build/source/games/sample_2d. The build/ folder is generated and can be deleted at any time, so a file saved there is not part of your game. Before you click Add, browse to source/games/<your_game>/private. If a file does end up in build/ anyway, every build prints a warning with its full path until you move it.

    To remove or rename a file, do it on disk and build again.

    The engine has no single header that includes all of it, so each file includes the engine headers it uses. You find the right header in the guide that explains the class, or at the top of the class's page in the API reference.

    Engine settings#

    buz::engine_settings is what you pass to the engine's constructor. Every field has a default, so you only name the ones you change, as main() above does with .window_title:

    field what it does
    window_width, window_heightsize of the drawable area in pixels
    window_titletext in the window title bar
    gpu_preferencewhich graphics card to run on; buz::adapter_preference::lowest_score is handy to test your game on weaker hardware
    clear_colorthe color the screen is cleared with before your game draws
    sampler_filterhow textures are filtered when scaled; buz::texture_filter::nearest keeps pixel art crisp instead of blurring it
    use_vsyncbuz::vsync::yes waits for the monitor (smooth, no tearing); no runs as fast as it can
    show_statsbuz::stats_overlay::yes starts with the stats overlay on (F3 switches it, see below)
    debug_controlsthe keys of the debug views, F1 to F4 unless you pick others; see below
    screenshot_path, screenshot_framesaves that frame as a png and quits; see below

    Settings that are on or off take a named yes or no, never true or false: settings.use_vsync = buz::vsync::no; reads as what it does. This is a rule throughout the engine; writing true where a yes or no is expected does not compile.

    Overriding settings at launch#

    The engine reads the argc and argv that main() passes on, so you can try other values without rebuilding. The settings in your code are the defaults, used when a setting is not on the command line:

    setting example
    -window_width, -window_height-window_width=1920
    -window_title-window_title=Demo
    -gpu-gpu=lowest, or -gpu=software for a software rasterizer (no graphics card needed, but slow)
    -screenshot, -screenshot_frame-screenshot=frame.png -screenshot_frame=300

    The engine logs a warning for every setting it does not know, so a typo like -window_widht=1920 shows up in the console instead of being ignored.

    Screenshots of one exact frame#

    Sometimes you want to know whether a change altered what the game draws, for example after you cleaned up your drawing code. You can find out by comparing a screenshot from before the change with one from after it, as long as both runs draw exactly the same frame. -screenshot=frame.png takes care of that: the game runs until frame 120, saves that frame as frame.png in its saved folder and quits (-screenshot_frame=300 picks another frame). Until then every frame lasts exactly 1/60 s and the keyboard and mouse are ignored, so the picture doesn't depend on how fast your computer is or what you pressed. That way, any pixel that differs between the two screenshots was changed by your code.

    Debug keys#

    A few keys show you what the engine is doing while your game runs. The engine handles F3 in every game, and buz::game_3d the three keys of the 3D views, so your game doesn't check them:

    key what it shows
    F3the stats overlay in the top-right corner: the frame rate, the frame time, and how many draw calls and instances the last frame used
    F13D only: the edges of every triangle instead of solid surfaces
    F23D only: every surface at its plain color, without lighting
    F43D only: hides the debug lines, and shows them again

    Each key switches its view on and off. If your game needs one of these keys for something else, give the view another key in debug_controls:

    The keys you don't name keep their default.

    Sharing your game#

    To share your game, package it:

    On both systems the archive holds the game and its content/ folder. That is everything the game needs, so whoever extracts the archive can run it on a machine without Visual Studio or your template.

    The script builds the shipping version (Release), and the package draws with the graphics api your build/ was generated for.

    There are three builds. Pick one in Visual Studio's configuration list, or give -development to the package script:

    build optimization logging use it for
    Debugnoneyesstepping through your code in the debugger
    Development-O1yestesting a package while you can still read the log
    Release (shipping)-O3 and link-time optimizationnothe package you share

    From your IDE#

    Each game also has package targets, in the solution's package folder: package_awesome_game for your OS and package_awesome_game_web for the browser (the web is only available with OpenGL). Build one like any other project, in Visual Studio with right-click and Build. The configuration you have selected picks the package: Release gives the shipping one, Development the one that logs. Debug is not a package, so the target asks you to switch. The output is the same as the script's, in package/.

    On the web#

    Add -web to get your game as a web page, for itch.io or your own site:

    The page runs your game compiled to WebAssembly, drawing with WebGL 2 (the browser's OpenGL). On itch.io, upload the zip as an HTML game. Some things to know:

    • The first web package downloads the Emscripten SDK, the compiler for the browser (about 1 GB, a few minutes). It is kept outside your project and reused by every later package.
    • The web package needs the OpenGL build/: the shaders are compiled by the shader compiler built there.
    • Browsers only play sound after a click, so the page says Click to play first.
    • The wireframe debug view (F1 in a 3D game) draws solid triangles: the browser's OpenGL cannot draw wireframes.
    • Double-clicking the page's index.html doesn't start the game: browsers refuse to load it from a file on disk. To try the page on your own machine, run a small web server that serves the unpacked folder. With Python, run python -m http.server -d package/awesome_game-web in your template folder and open http://localhost:8000 in your browser.

    OpenGL, DirectX 12 and Vulkan#

    The engine draws with OpenGL unless you ask for something else. OpenGL is the easiest of the three to read, and most tutorials use it, so start there: when you want to see how the engine draws, Under the hood and the code in source/engine/rhi/private/opengl are written to be read.

    Your template also has the modern api of your OS: DirectX 12 on Windows, Vulkan on Linux. They give you more control and more to manage yourself (memory, synchronization, command lists), the way console and PC engines work. Switch when you want to learn one of them. Your game code stays the same; only the engine's backend changes.

    graphics api Windows Linux
    OpenGL (the default)generate.bat./generate.sh
    DirectX 12generate.bat vs2026-d3d12
    Vulkan./generate.sh linux-vulkan

    To switch, run the generate script with the preset from the table and build again. All presets use the same build/ folder, so the build and run scripts keep working as before. To go back to OpenGL, run the generate script without a preset. When the game starts, the console tells you which api it uses, for example Graphics api: OpenGL.

    If you open the template folder directly in Visual Studio, VS Code or CLion, pick the preset from the IDE's CMake preset list instead.
