    Guided exercise: Use the 3D template and write the collision code yourself (see Guided experiences). The engine provides buz::aabb in core/aabb.h and buz::debug_draw::box for drawing boxes. You will implement the overlap, movement and visibility tests.

    What you will build#

    You will stop the player from walking through walls, then use the same level geometry to check whether a guard can see the player.

    For this exercise, represent the player and solid objects with axis-aligned bounding boxes, or AABBs. These boxes stay aligned with the x, y and z axes; they do not rotate with the object. Each box stores two corners: min, with the lowest coordinate on each axis, and max, with the highest.

    Draw the boxes with buz::debug_draw::box before implementing collision. Check that they match the walls, crates and player. A box in the wrong place will produce incorrect collisions even if the tests are correct.

    The examples below are pseudocode. Implement and test each operation separately before connecting it to the game.

    Step 1: test whether two boxes overlap#

    Start with one axis. If one box covers x = 0 to 2 and another covers x = 1 to 3, their x ranges overlap. If the second starts at x = 3, there is a gap.

    Use < here. Two boxes whose faces only touch should not count as overlapping. This lets the player rest against a wall without being treated as inside it.

    Check: Test overlapping boxes, separated boxes and boxes that just touch. Also test boxes that overlap on two axes but are separated on the third.

    Step 2: stop the player at walls#

    For a first version, move the player's box and test it against the walls. If it overlaps a wall, restore its previous position. This stops the player from entering walls, but it also cancels movement along a wall when the player approaches diagonally.

    To allow sliding, resolve one axis at a time. Move along x and correct any overlap, then do the same for y and z.

    Shift both corners of the box by the same amount so its size stays the same. Use the corrected box position to update the player's position. This approach assumes the player starts outside the walls.

    For example, if a wall blocks movement along x but allows movement along z, only the x movement is stopped. The player can still slide along z.

    Check: Walk straight into a wall, diagonally along it and into a corner. Check both positive and negative movement directions.

    Fast movement and thin walls#

    Testing only the final position can miss a wall. If one update moves the player completely through it, the final box no longer overlaps the wall. This is called tunneling.

    For the hard level, check the path of each axis movement. Find walls ahead that overlap the player's box on the other two axes, calculate the gap to each wall and limit movement to the nearest gap. Test this with a deliberately large movement step and a thin wall.

    Step 3: find where a ray hits a box#

    A ray starts at an origin and travels in a direction. For this exercise, also give it a maximum distance. Normalize the direction so the parameter t in origin + direction * t represents distance.

    The slab method checks one axis at a time. On each axis, calculate when the ray enters and leaves the range between box.min and box.max. The ray hits the box if there is a distance interval where it is inside all three ranges at once.

    If the ray is parallel to an axis's boundary planes, there is no division to perform on that axis. Its origin must already lie within that range. A ray starting inside the box reports distance 0 with this implementation.

    Draw the ray with buz::debug_draw::line. Draw a small buz::debug_draw::sphere at origin + direction * enter when it hits.

    Check: Test a hit, a miss, a ray parallel to a face and a ray starting inside the box. A box beyond max_distance should not produce a hit.

    Step 4: check line of sight#

    To check visibility from point a to point b, calculate:

    Cast this ray against the level's blocking boxes, with distance as its maximum distance. If an obstacle is hit before b, it blocks the view. A wall behind b should not matter.

    Exclude the guard's and target player's own boxes from the obstacle test. If a and b are the same point, handle that case before dividing by distance.

    Check: Place a wall between the two points, then move it behind the target. Draw the tested line so you can see which points it connects.

    Step 5: limit the guard's view#

    A clear line of sight does not mean a guard should see through the back of its head or across the whole level. Add distance and direction checks.

    Choose a target point on the player, such as the chest. Let to_player be the vector from the guard's eyes to that point. Test these conditions in order:

    1. Distance: length(to_player) < view_distance.
    2. Direction: dot(normalize(to_player), forward) > cos(half_angle).
    3. Obstacles: the line of sight to the target point is clear.

    forward must be a unit vector pointing where the guard is looking. half_angle is half the cone's full opening angle; pass it in radians to the cosine function. The dot product is 1 when the two directions match and decreases as they turn apart. Comparing it with cos(half_angle) checks whether the target is inside the cone. Handle a zero-length to_player before normalizing it.

    The distance and direction checks avoid ray tests for players who are already too far away or outside the guard's view.

    Draw the view cone with buz::debug_draw::cone and change its color when the guard sees the player. The target point matters: a crate may hide the player's chest while leaving the head visible. As an extension, test several points and decide how they contribute to visibility.

    Check: Move the player outside the range, behind the guard and behind a wall. Each should prevent detection for a different reason.

    Levels#

    Complete the basic level before adding the intermediate and hard features.

    Basic

    • Draw every collision box with debug drawing while developing.
    • Use strict overlap tests so touching a wall does not count as being inside it.
    • Stop the player at walls.

    Intermediate

    • Resolve movement one axis at a time so the player can slide along walls.
    • Test ray-box intersection separately: hit, miss, parallel ray and ray starting inside.
    • Check guard visibility using distance, view cone and line of sight, in that order.

    Hard

    • Check the movement path so large steps cannot carry the player through thin walls.
    • Build the level's collision boxes from col_* nodes in the level file (see Models).
